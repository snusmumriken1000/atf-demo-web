実行環境の仕組み

🛠 ハーネス

エージェントを動かす骨組み

  • エージェント定義 — .claude/agents/ に 8 体。プリセット「Web アプリ開発チーム」を atf-demo-web 向けにカスタマイズ
  • 入出力フロー — エージェント間の受け渡し経路を 6 本定義(下の構成図に対応)
  • チームマニフェスト — .claude/team.json がチーム構成の単一情報源(再生成・可視化の入力)
  • Issue 起点のタスク供給 — issue-manager が GitHub Issue(snusmumriken1000/atf-demo-web) を起票・整理し、各エージェントへ振り分け
  • PR ベースの変更フロー — ブランチ作成 → push → gh pr create で変更を Pull Request 化(Issue 番号を紐付け)

🚧 ガードレール

逸脱を防ぐ制約

  • 役割スコープの限定 — 各エージェントは定義された責務の範囲でのみ作業(構成は上のカード参照)
  • チーム規模の上限 — 標準構成(最大 5 体)でエージェント数を制御
  • 既存定義の保護 — 導入時に既存の .claude/agents/ を上書きしない(上書きは --force 必須)
  • Issue 起点の着手制限 — 対応する Issue のない作業には着手せず、先に Issue の起票を提案
  • 人間のタッチポイント — Issue 着手前のユーザー承認 / PR マージはユーザーが実行
  • マージの実行主体 — エージェントは PR 作成まで。マージはユーザーがレビューして実行

🔄 フィードバックループ

結果を観測して改善につなげる仕組み

  • 実行記録の自己申告 — 全エージェントが作業完了時に .claude/atf-logs/runs.jsonl へ 1 行追記(現在 0 件)
  • 失敗の可視化 — status: failure の記録を実行記録テーブルに ❌ 表示(現在 0 件)
  • ダッシュボード再生成 — atf report で最新の実行記録を反映した本ページを再生成
  • Issue へのトレース — 実行記録・コミットメッセージに Issue 番号を残し、進捗を Issue 上で追跡
  • PR へのトレース — 実行記録の outputs に PR の URL を残し、変更を PR 単位でレビュー・追跡

エージェント

architect

機能追加や変更の実装方針を設計するアーキテクト。実装前の設計検討、影響範囲の調査、アーキテクチャ上のトレードオフ判断が必要なときに使う。

implementer

設計方針に沿ってコードを実装する実装担当。機能追加・バグ修正・リファクタリングの実作業を任せるときに使う。

test-engineer

テストの作成・実行・失敗解析を担当するテストエンジニア。変更の検証、テスト追加、フレーキーテストの調査に使う。

code-reviewer

変更差分をレビューするコードレビュアー。実装完了後の品質チェック、マージ前の確認に使う。

doc-writer

README・API ドキュメント・変更履歴などのドキュメントを作成・更新するライター。ドキュメント整備が必要なときに使う。

env-builder

エージェントチームの実行環境(ハーネス・ガードレール・フィードバックループ)の設定とコンテキストファイルの整備を担当する環境ビルダー。チーム導入直後のセットアップや運用ルールの点検に使う。

issue-manager

GitHub Issues の起票・整理・優先順位付け・クローズ判断を担当する Issue マネージャー。タスクの Issue 化と進捗管理に使う。

orchestrator

チームのサブエージェントをまとめ上げ、タスクの計画から完了まで開発を推進するオーケストレーター。「開発を進めて」と依頼されたときの起点として使う。タッチポイントでは一時停止してユーザーの承認を仰ぐ。
